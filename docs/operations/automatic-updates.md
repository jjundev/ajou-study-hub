# Automatic update preparation

The initial `study-hub-update.yml` workflow verifies only. It has no publishing stage, Cloudflare credential, or ledger credential. Automatic publication remains disabled until later readiness and activation tasks complete. The existing manual release still requires fresh human proof within 24 hours.

## Trust and execution order

Only `jjundev/ajou-study-hub`, `refs/heads/main`, and the workflow from that same trusted app SHA may run. Pushes and manual dispatches are accepted; PRs, forks, and `pull_request_target` are not accepted. The optional `source_repository` input is checked against the five configured course repositories before token creation. The only mode is `verify`.

The job uses Ubuntu 24.04, Node 24.15.0, a 60-minute timeout, and the `study-hub-production` concurrency group without cancellation. App permissions are Contents:read and Actions:read. All external actions use full commit SHAs; their official `action.yml` contracts were checked through the GitHub API during implementation on 2026-10-26.

The app is checked out to `app/`; sources are sibling checkouts in `sources/<course-id>/`. The trusted tracked files, Git index and HEAD, effective and local Git configuration, hooks, and selected credential/runtime files are fingerprinted immediately after app checkout. This layout preserves source ownership and reserved output checks, and the verification project continues to be resolved from the installed module location.

An explicitly approved bootstrap runs `npm ci --ignore-scripts` **before** Reader token creation solely to load the pinned TypeScript resolver. The Reader App has Contents:read on the five source repositories only. Its private key is passed only to the token action; its token is passed only to revision resolution, fixed-SHA checkouts, and revocation. No credential is a job-wide environment variable, and checkouts use `persist-credentials: false`.

All five `main` SHAs are resolved once with the existing resolver. Checkouts use those SHAs throughout the run. The token is explicitly revoked before normal `npm ci`, browser installation, synthetic tests, or material execution. The token action retains its post-job revocation fallback. Failed revocation blocks subsequent validation. Cancellation or runner loss can prevent explicit cleanup; installation tokens remain subject to GitHub's expiration and the action's cleanup behavior, so live lifecycle behavior must be checked in preparation.

Only the trusted app's commands run. Source repository scripts are never invoked. The preflight rejects symlinks and special files, limits source files to 100,000, each file to 256 MiB, all source bytes to 2 GiB, and requires 4 GiB free before reading material. Existing source path validation and final bundle limits still apply. These checks occur after clone; clone/download disk exhaustion can still fail the job safely. Typecheck, unit tests, and Chromium/Firefox/WebKit E2E run before the material build. Both build and content verification explicitly use `.local/ci-sources.json` in the same checkout.

## Boundary guarantee and mandatory remaining work

**The process boundary is detection only. Passing this workflow does not establish enforceable isolation against malicious code running with the runner user's permissions. Task 6 must keep `readiness.isolation` false until a concrete separate trust boundary is implemented and tested on actual Linux.** A process scan or a synthetic test must never be recorded as that proof. Future deployment credentials must not be added on the assumption that this check alone makes them safe.

`assertCleanBoundary(project, trustedFiles)` rejects a changed tracked checkout, index, HEAD, effective configuration, hooks, credential/runtime fingerprint, surviving Reader environment, or relevant live process. The workflow also checks each sibling source checkout's effective Git configuration for credential helpers, authentication headers, and command/URL overrides. Linux reads only process ID, parent ID, user ID, executable path, and working directory. It excludes its own ancestor chain, detects workspace services and known browser/Node/build runtimes even after reparenting, and never dumps arguments/environments or kills processes. An unsupported platform or unreadable metadata fails closed. Same-UID tampering with the checker, baseline, dependencies, or an unrecognized reparented process remains outside this detection guarantee; there is also a scan-to-next-step race.

Task 6 must perform the first actual Linux run, check Korean paths and all three browsers, validate clean and intentionally surviving harmless owned processes, verify Reader revocation and credential absence, and establish actual isolation separately. Windows unit tests and synthetic process rows do not satisfy these requirements. No private material/API/session/DPAPI access, remote change, deployment, or secret setup was performed to implement this workflow.

## Diagnostics and recovery

Application, test, browser, and material command output is suppressed; failures expose fixed safe error codes. No raw exception, credential, process argument, environment, HTML/PDF material, proof/session file, `dist/`, `.local/`, or `.reports/` is uploaded. A successful run uploads only `app/ci-summary.json`: validated app SHA, source count, and a verification-only detection code, with a hard 1 MiB bound and seven-day retention. Dependency and action service logs remain governed by GitHub Actions; do not enable debug tracing around credentials or private material.

A failure requires investigation with the matching safe code and pinned revision identity. A verification run does not mutate the publication ledger or retry a publication. Local-only changes, untracked files, and unpushed commits are absent from remote source checkouts. The published site is not replaced or changed by this workflow.

## Emergency withdrawal and isolated rehearsal

`disableEndpoint(settings, expectedWorkerId, request, token)` validates the fixed production name `ajou-study-hub`, account, independently approved immutable Worker ID and sole workers.dev address before writing. It inventories Worker identity, disabled previews, account subdomain, custom-domain references and zone routes; ambiguity blocks. The only write is `POST /accounts/<account>/workers/scripts/ajou-study-hub/subdomain` with `{ "enabled": false, "previews_enabled": false }`. It does not read production script/material content or change Access configuration. It requires read-back of the same identity/configuration with subdomain disabled and an external 404 with the exact supported `error code: 1003` response. Generic errors, Access login/denial, redirects, timeout or unreadable state are not confirmation. Real Cloudflare withdrawal response compatibility is still untested; an unsupported response blocks confirmation after the write and requires operator inspection, never a retry.

Public Worker probes omit API authorization and cookies, disable redirects and have bounded bodies/time. API errors become fixed generic failures. Production reactivation is deliberately absent from unattended code. An operator must inspect the exact disabled Worker and current Access protection, then explicitly authorize a separate enable action for that same target and verify production access. An uncertain write must be reconciled by reading state before any further action.

`rehearseRecovery` accepts only a separately prepared `ajou-study-hub-recovery-test` target with explicit account/immutable ID/address. It requires no bindings, assets, domains or routes; exact source bytes `export default {fetch(){return new Response("recovery-test");}};`; a single supported JavaScript download identified as `index.js`; and exact public `recovery-test` marker before and after. The shared source adapter accepts `application/javascript` with exact `Content-Disposition: attachment; filename="index.js"`, or the observed `multipart/form-data; boundary=<60 lowercase hex characters>` with no top-level disposition. Multipart must contain exactly one untyped string part with the sole header `Content-Disposition: form-data; name="index.js"`, the exact literal, CRLF framing and final CRLF. Extra parts/headers/bytes, BOMs and other formats fail closed. Source bodies are capped at 16 KiB before consumption; declared lengths must match. Restore occurs only after API and external disabled-state confirmation. It is never a `finally` cleanup on an uncertain result. This unit-tested adapter does not constitute an actual recovery rehearsal or production-equivalence proof.

Remaining live work requires independent code review and the applicable authorization: actual Linux/browser/path/space checks and enforceable trust boundary; three minimally scoped App installations and revocation/expiry behavior; private ledger nonforce/read-back conflict tests on a fixed rehearsal ref; actual Cloudflare permissions and empty-target withdrawal/restoration equivalence; production human/material/manifest and remote-source difference acceptance; and actual included Actions allowance/overage blocking/Cloudflare Free confirmation. ## Dedicated recovery operator

After independent review and within the approved live preparation, a local operator may run `npm run access:rehearse-recovery -- --create-empty-rehearsal`. The only credential input is the existing `CLOUDFLARE_API_TOKEN` environment variable; do not pass it on the command line. The command rejects CI, unknown flags, target/account/name/source overrides, an existing reserved name, or any prior creation receipt. It validates canonical deployment settings and the genuine automation baseline against fresh production Access/Free/identity/version observations first. It does not approve or refresh the baseline.

Creation uses the documented POST Worker endpoint with the fixed reserved name, logging disabled, no tail consumers, endpoint disabled and previews explicitly false. It records the returned immutable ID immediately, verifies it through the same account's inventory and ID endpoint, then uploads only literal `index.js` using multipart metadata with compatibility date `2026-10-24`, no bindings/assets and logging disabled. Raw source bytes, settings, identity and disabled endpoint are checked before enabling the rehearsal endpoint. Every subdomain write explicitly includes `previews_enabled:false`. The exact empty rehearsal then disables, observes withdrawal and restores; the operator checks empty settings/source again after restoration. Production has no write path in this CLI.

Fixed local files are `.reports/recovery-target.json` (owned target and attempt phase), `.reports/recovery-result.json` (latest bounded outcome), and `.reports/recovery-operation.lock` (exclusive local invocation). Never treat a receipt as overall automatic-publication readiness. Intent phases or `unverified` mean an operation may have taken effect without a confirmed result. Failed attempts now retain `enable-intent`, `rehearsal-intent` or `staged-resume-intent` once reached; these phases are ineligible for staged resume. Keep that evidence; do not delete or rewrite it to retry. A hard interruption may leave the lock too; investigate the original process and remote state before any separately authorized reconciliation. The command never deletes a Worker, overwrites a preexisting target, retries a write or silently recreates one.

`npm run access:rehearse-recovery -- --verify-existing-rehearsal` requires the exact previously recorded owned ID/account/URL and matching current baseline. It never uploads or recreates source. It proceeds only if the owned endpoint is already **enabled**, still strictly empty and has previews disabled. This mode does not enable disabled leftovers or finish an uncertain restore.

After independent review, the controller may explicitly invoke `npm run access:rehearse-recovery -- --resume-owned-staged-rehearsal` to reconcile the known legacy staged target. It accepts only a canonical owned receipt with phase `unverified`, `productionUnchanged:true`, and both confirmation flags false, bound to the genuine current baseline, account, immutable ID, fixed name and derived URL. Missing/null ownership, verified receipts, other phases and extra arguments fail. Fresh production and rehearsal identity/configuration/source/host/zone checks must prove the endpoint disabled with previews false. Worker GET must explicitly report observability disabled; settings may omit observability only after that same-attempt proof, and any present settings observability must explicitly be false. Logging, empty bindings/assets/flags/tails/references and all other guards remain enforced. Only then does the command persist `staged-resume-intent`, enable that owned endpoint with previews false and perform the normal rehearsal. It never creates, uploads, restages or deletes. A failure retains the non-resumable intent; future disabled rehearsal failures cannot be recycled into this path by rerunning it. No receipt provenance or baseline approval is rewritten.

Production inspection is attempted again after success or partial failure. Drift or an unavailable post-read records `productionUnchanged:false`; no cleanup restore/delete follows. Unsupported source-download format or external disabled response likewise leaves an unverified result, potentially with the rehearsal endpoint disabled. Raw source validation rejects even a UTF-8 BOM before the approved literal. The multipart adapter matches the safely observed staged-target frame; real disable-response compatibility and complete recovery equivalence remain unproven until an actual reviewed run. No real rehearsal was executed while implementing this operator.

## Local GitHub App role proof

After independent review, the authorized controller can run `npm run ci:prove-permissions` locally with no arguments. Supply the existing PEM values only through the operator process environment: `STUDY_HUB_READER_PRIVATE_KEY`, `STUDY_HUB_DISPATCH_PRIVATE_KEY`, and `STUDY_HUB_LEDGER_PRIVATE_KEY`. Never put values in command arguments, terminal output, reports or plaintext files. The operator captures and deletes these variables before validation or network activity; it never launches child processes or a browser, reads key files, creates Apps/keys, changes secrets, or writes repository contents/refs. CI and all arguments/target/base-URL overrides are rejected.

The trusted project root fixes `.local/github-reader-app.json`, `.local/github-dispatch-app.json` and `.local/github-ledger-app.json` as public identity receipts. The authoritative projection must match account `jjundev`, selected repositories, App/installation IDs, slug, exact permissions and the fixed DPAPI key-store label. The key-store path is checked as a public label and never read. Historical UI fields or `apiTokenPermissionsTested` do not count as live proof. Reader uses App 5478307/installation 175423301 with Contents:read on exactly the five configured course repositories; Dispatch uses 5478852/175430013 with Actions:write on `jjundev/ajou-study-hub`; Ledger uses 5478953/175431663 with Contents:write on `jjundev/ajou-study-hub-state`. Every role includes mandatory Metadata:read.

The operator signs RS256 JWTs with a maximum ten-minute claim lifetime, checks the authenticated App and installation identities, then issues one token per role with explicit repository names and exact minimal permissions. It checks returned permissions and repository selection, a future expiry within the documented one-hour bound, and the exact private repository inventory through complete bounded pagination. No write probe is used. Every recovered issued token is revoked in `finally` through `DELETE /installation/token`, requiring 204, followed by an authenticated inventory probe with the same revoked token requiring 401. Invalid exchange metadata also triggers cleanup if a usable token was returned. Exchanges and revocations are never retried. Unknown responses or a hard interruption may leave an unrecoverable token until GitHub expiry; preserve the unverified result and investigate before another attempt.

All requests stay on `https://api.github.com`, with manual redirect handling that rejects redirects and Location headers without following them. Each request has a ten-second timeout and one-MiB response limit; each role has a twelve-request budget, including cleanup, and at most five inventory pages. Reports contain only fixed public identities, requested and validated observed scope, expiry, safe status codes and explicit limitations. Raw responses, exception messages, PEMs, JWTs and tokens are discarded.

The canonical result is `.reports/github-app-permissions.json`. Individual role `verified` fields and `rolesVerified` can succeed. Overall `verified` and `stateActionsDisabled` remain **false**: GitHub's [read-only repository Actions-settings endpoint](https://docs.github.com/en/rest/actions/permissions#get-github-actions-permissions-for-a-repository) requires Administration:read, which these minimal Apps deliberately lack. The command exits nonzero even when all role proofs pass and explains the outstanding setting proof. The controller must retain separate authorized evidence of disabled state Actions; no broader permission is requested. This report also does not attest to private App-registration visibility, all other account installations, or natural expiry after waiting an hour. It never issues `readiness.permissions=true`; private-ledger conflict/read-back and Cloudflare permission proofs remain separate gates.

Endpoint contracts were checked against GitHub's official [JWT guidance](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app), [installation-token generation and scope guidance](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), and [installation inventory/revocation API](https://docs.github.com/en/rest/apps/installations) on 2026-10-27.
